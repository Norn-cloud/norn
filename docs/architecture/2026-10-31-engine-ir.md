# Architecture amendment: engine consumes canonical IR

Accepted: 2026-10-31.

`norn-ir` owns the canonical shared contracts. `norn-engine` is a ring-1
host consumer and may depend directly on `norn-ir`. This amendment governs
the engine export; it does not add an engine implementation or change release
policy.

## Declared dependency row

| Crate | Ring | Allowed direct Norn dependencies |
| --- | --- | --- |
| `norn-engine` | 1 | `norn-kernel`, `norn-cell`, `norn-checker`, `norn-projections`, `norn-ir` |

All unlisted Norn edges remain forbidden for every dependency kind. In
particular, `norn-ir` may not depend on `norn-engine`. Ring 0 remains pure,
portable, synchronous and free of host IO and native runtime dependencies.

## Ownership and public evidence

- [Canonical artifact envelopes](../../crates/norn-ir/src/lib.rs) belong to
  `norn-ir`, including their closed payload vocabulary and serde wire form.
- [Exact runtime values](../../crates/norn-ir/src/runtime.rs) and
  [Function manifests, invocations and receipts](../../crates/norn-ir/src/function.rs)
  are portable contracts, independent of the host that executes them.
- [Checker diagnostics and admission](../../crates/norn-checker/src/lib.rs)
  remain checker-owned. The IR diagnostic wire type and checker diagnostics
  are distinct types; this amendment does not make them interchangeable.
- [The existing cell boundary](../../crates/norn-cell/boundary.json) already
  permits a ring-1 host to consume IR alongside the kernel and checker.
- [The guard policy](../../crates/norn-skeleton-guard/src/lib.rs) enforces
  dependency direction and ring-0 host restrictions.

Host errors, storage scope keys, settings lookups and execution machinery
remain engine-owned. Consuming IR fields does not transfer those host
responsibilities into IR. Checker admission, kernel decisions and cell
commit ordering and durability retain their existing authority.

## Compatibility requirements

Keep the canonical definitions in `norn-ir`; do not move them into the engine,
create a shared crate, introduce a facade, or copy them into host DTOs.
Preserve Rust type identity, serde representations, exact decimal precision,
diagnostic codes and canonical hashes. Use the existing canonical hashing
implementation rather than a serialization round trip or duplicate encoder.

The enforceable guard row may precede the exported crate only after the guard
supports predeclared rows without requiring workspace membership. It must not
require a placeholder implementation or a known-violation entry. Subsequent engine
slices must provide functional behavior, pass the normal gates and retain
these ownership and authority boundaries.
