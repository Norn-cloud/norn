# norn-checker

`norn-checker` is a ring 0 crate (pure, portable semantic core): shared contract/lifecycle diagnostics. Its dependency boundary is in `boundary.json` and enforced by `norn-skeleton-guard`.

It holds every check over the typed IR in `norn-ir` (T1-CHK-1, #2524, moved them here with zero behaviour change): artifact-envelope and graph-load checks (`envelope`), ontology packs (`ontology`), sealing (`sealing`), the quantity-ledger checker and posting boundary (`quantity_ledger`), and generic exact posting admission (`posting`). The moved validators still emit the legacy `norn_ir::Diagnostic` wire type; `Diagnostic` (stable code, severity, message, JSON-pointer `Span`) is the checker model they map onto via `check_artifact` / `Diagnostic::from_legacy`. Set checks are T1-CHK-3; the C/WASM ABI T1-CHK-4.

## Diagnostic codes and JSON output (T1-CHK-2, #2525)

- `codes::REGISTRY` (`src/codes.rs`) lists every code the crate can emit with its tier (T0–T7, 2026-08-27 ruling), severity, message template, and `since` version. Codes are never renamed or reused. `tests/code_registry.rs` scans the non-test source: every dotted code literal must be registered, and every registered code must be emitted, so adding a diagnostic means adding a registry row. Its non-code literal allowlist must equal `tests/non_code_literals.baseline.json`, which CI keeps shrink-only (`crates/norn-checker/scripts/non-code-literals-shrink-only.sh`).
- `conformance/diagnostic-codes.json` is the checked-in conformance manifest (`codes::conformance_manifest()`) for other frontends (#2425).
- `diagnostics_to_json` is the stable diagnostic JSON format (`norn-checker/diagnostics@1`); `check_artifact_json` is the decode-then-check JSON admission entry point. The implemented Rust `norn check` command emits an admission report JSON envelope, not this standalone diagnostic format.
- `fixtures/invalid/manifest.json` (repo root) lists invalid artifacts with `file`/`reason`/`error_at`/`code`; `tests/diagnostic_snapshots.rs` asserts each is rejected with that code at that JSON pointer and pins the full JSON output in `tests/snapshots/`. `fixtures/rule-ir-v2/invalid/manifest.json` is the same for the RuleIR v2 Norn-profile rejection corpus (one fixture per profile code; `jdm_profile.rs`), snapshotted in `tests/snapshots/rule-ir-v2/`.
- Regenerate the manifest and snapshots with `NORN_CHECKER_UPDATE_GOLDENS=1 cargo test -p norn-checker --test code_registry --test diagnostic_snapshots`, then review the diff.

## Check receipts (#2851)

- `check_artifact_set_with_receipt` runs `check_artifact_set` under a resource-limit profile and issues a `CheckReceipt` (Norn1 canonical JSON with its own content hash). It binds the artifact-set identity (each candidate and base envelope as `(artifactId, version, sha256)`, plus one set hash), the `LimitProfileRef` (`norn.limits/1` by default), the set's ZEN Expression `TypeEnvRef` (`norn.expr.env/1`, derived only for a clean set, with only `actor` bound) beside the expression checker profile (`norn_expr::check::CHECKER_PROFILE`, currently `norn-zen/6`, published in `crates/norn-expr/src/check.rs`), the checker name and version, the identifier admission profile (`norn-identifiers/1` for new admissions), and a digest of the findings. A clean set whose environment cannot be derived is rejected with `artifact_set.expression.environment_underivable`.
- Every EntityIR v2 expression site (computed properties, invariants, lifecycle guards) is parsed at T2 (T1-ONT-2, #2515; `object_types::check_zen_syntax`), and sites read their object through `self`. Boolean invariant type checking is implemented, including refusal of link/inverse-role reads. Remaining per-site type checking and environment references (each site's `self`/`input` binding) belong to T1-EXPR-5 (#2523). The golden receipt is `tests/golden/check-receipt.retail.json`; regenerate it with `NORN_CHECKER_UPDATE_GOLDENS=1 cargo test -p norn-checker --test check_receipt` and re-pin its hash.

Retained definition receipts are verified against their recorded checker/profile and exact artifact set before re-admission. Legacy `receipt@1` evidence retains the historical identifier policy; upgraded `receipt@2` evidence records that policy explicitly. New installs and updates always enforce the current identifier limits. Identifier limits are defined in `norn-ir::identifier_limits`.

### Exact-source receipt identity (HOST-RECEIPT)
SOURCE-DECODE-VERBATIM: preparing an exact source removes only inline editor fields. The semantic source, decoded string values and object keys retain their submitted Unicode spelling, including decomposed artifact ids and executable text. Semantic decoding does not apply Norn1 normalization.
SOURCE-HASH-CORRESPONDENCE: artifact hashes still use the existing Norn1 canonical bytes of that extracted source. Unicode normalization belongs only to hashing; preparation, challenge admission and writer → source-verification round trips agree on the verbatim semantic model. `source_decode_verbatim_and_hash_correspondence` exercises both candidate/base positions with decomposed ids, keys and executable literals, alongside editor extraction.
RECEIPT-EXACT: receipt identity is injective over exact canonical source (assuming SHA-256 collision resistance).
WRITER-CLOSURE: every writer requires `ReceiptSources` from exact candidate/base runtime sources; the convenience source writer uses that same constructor. CHALLENGE-PHASE: protected ingress retains verbatim sources; Norn1 collisions still refuse at admission. CHALLENGE-BUDGET: numeric preflight and array admission precede runtime source construction. Typed verification refuses @5–@7; historical @1–@4 readers and hash-only reconstruction remain. RETAINED-IDENTITY: rechecks compare exact semantic identity before reusing an attested profile; a changed install uses current admission. CONTEXT-BASE: a different checker base is refused. `tests/check_receipt.rs` enumerates ordinary, flow-map, fresh install, retained install, flow-map install and verified recheck writers against both precision vectors in both layer positions.
Conformance in `tests/check_receipt.rs`: EXACT-INTEGER (`9007199254740992` / `9007199254740993`),
EXACT-DECIMAL (`0.1234567890123456789012345678` / `0.1234567890123456789012345679`),
EXACT-LITERAL (`25` / `26`), EXACT-VERIFY (substitution refusal), EXACT-ORDER (key reordering).
Both positions are covered. Writers emit @5 (mapless), @6 (flow map), @7 (law origins); readers retain @1–@4 until contract cleanup.
LEGACY-INLINE: verify original inline-layout source, then recheck after extraction; `old_receipt_hashes_recover_and_recheck_after_inline_layout_extraction` covers it.
ABI-PROFILE: duplicate JSON keys fail the Norn1 source parse and produce an ABI error; no receipt is issued.
